OneFit-Engine (Raku) performance benchmark
===========================================

Date: 2026-09-21

Methodology
-----------
Two deployments, both updated to onefite-c-code main @ 6633911 (post
Numerical-Recipes replacement, FFT half-length-complex-FFT rewrite,
sqgausn quadrature-node caching, Florence removed to a separate
extensions bundle) and minuit @ b842e5b (MNE=2000/MNI=1000):

  - .105 (192.168.64.105): Go port (onefite-native + onefite-gui),
    driven through the live onefite-gui HTTP API (port 9143,
    POST /api/run + GET /api/sessions/<id> polling). Timed via the
    server's own createdAt/completedAt timestamps (excludes HTTP
    polling overhead).
  - .73 (192.168.64.73): Raku port (OneFit-Engine), driven through the
    live start-web-engine HTTP API (port 8142, POST /fit multipart,
    synchronous - the response IS the result zip). Timed as full
    client-side wall-clock HTTP round-trip (upload + fit + zip
    download), so these numbers include real network/multipart
    overhead the Go API's own timestamp-based numbers don't.

"Raku (Mac native, s)" is the pre-existing historical baseline
(perf-check-report-1.xlsx): the original bin/onefite, timed natively
on a Mac, no HTTP layer at all - included for context, not a like-for-
like comparison with the two HTTP columns.

fit-methods for the three (--hybrid) rows was "simp scan min" (minos
omitted) at the user's request - not directly comparable to the
historical baseline's own default "simp scan min minos" for those
three rows specifically.

pre-final-C16lyo is a new fixture (RNordio_poli + Torrey1 + ODFSmA x2 +
OPF x2, 3 data sets, 62 points, 13 params/7 free, Global) with no
historical baseline - the only row here that actually exercises the
OPF/sqgausn code path the quadrature-caching fix targets.
